# Independent review of Outbreak Ledger v0.4

Reviewer: Codex, assisting Dr Tambe Elvis Akem. Review date: 4 November 2026.

## Assessment

Version 0.4 materially expands the prototype: automatic report-family routing, a shared workspace, multi-disease weekly-table extraction, source-linked narrative statements, human retagging and issue threads. It is a more persuasive demonstration of public-report reuse than the earlier single-disease interface.

However, it is not yet reliable as general multi-event intelligence infrastructure. Important semantic boundaries are absent from exports, some calculations and issue linking. Passing the included tests does not cover these failure modes. Correct event attribution and preservation of meaning should precede more formats, higher upload limits or AI integration.

## Setup failure: cause and remedy

The supplied outer ZIP contains an inner application ZIP and three development CSVs. The inner application ZIP does contain requirements.txt beside START_OUTBREAK_LEDGER.bat. The user's error path points into Windows AppData/Local/Temp and names the ZIP, strongly suggesting the launcher was opened from within a compressed archive. Windows can copy the selected batch file to a temporary directory without extracting its companion files.

The pip update notice is informational. The fatal error is inability to find requirements.txt. A network failure would produce a different error. The original launcher's generic advice to check internet therefore misdiagnoses this case.

Extract the complete application into a permanent folder, for example Documents/OutbreakLedger_v04. Open the extracted folder, confirm requirements.txt, outbreak_ledger and config are present, and start its launcher. Do not reuse the temporary virtual environment mentioned in the error; a new extracted folder creates its own environment.

### Changes in this startup-fixed copy

- Requirements, application code and qualitative configuration are checked before environment creation.
- pip receives the absolute path to requirements.txt.
- Failure to change into the application folder is reported explicitly.
- Missing companion files produce Extract All instructions.
- Dependency failure is no longer automatically described as an internet problem.
- The download is repackaged as one application folder, without a ZIP nested inside another ZIP.

The Python extraction engine, web interface, analytical rules and schemas are unchanged. This is a startup correction plus review, not a release fixing the analytical findings below. Actual execution of the batch file remains untested because Windows is unavailable here.

## Confirmed high-priority findings

### 1. Narrative extraction can assign the wrong disease and country

Location: config/who_wer.yaml, lines 41–47; outbreak_ledger/extract.py, narrative_claims().

The generic "as of ... a total of ... confirmed cases and ... confirmed deaths" pattern unconditionally supplies disease BVD and geography drc. It does not require evidence that the sentence concerns BVD or DRC.

Constructed counterexample: a page titled "Mpox in Kenya" states: "As of 11 October 2026, Kenya had reported a total of 123 confirmed cases and 4 confirmed deaths from mpox." The extractor produces BVD/DRC cases=123 and deaths=4.

This is a reproduced code failure, not a claim that the submitted real corpus contains that erroneous row. Source linkage and human review do not excuse knowingly incorrect automatic attribution.

Required change: require disease and place evidence from the sentence/section, expose the attribution evidence for review and abstain when ambiguous. A BVD-specific rule must be explicitly anchored to BVD and DRC, with negative tests for other diseases and countries. Approval must require an identified and reviewed event.

### 2. Numeric exports and the observation interface lose essential disease context

Location: outbreak_ledger/web.py, line 177; outbreak_ledger/web_assets/app.js, filtered(), renderQueue(), renderDetail().

The numeric CSV includes geography, indicator and case classification but omits disease, event identifier, report family, period_start and period_label. Multiple disease rows from one national report can therefore have the same apparent exported meaning. Report number and source hash allow manual lookup but are not adequate substitutes for the missing disease column.

The numeric queue/detail also omit disease from their displayed meaning. Search does not include disease. The qualitative interface does show event tags, so the two review workflows are inconsistent.

Required change: include disease and stable event ID in every exported row and review card; add family, complete period bounds, period convention and source definition. Provide disease/event filters and a route from each event card to its numeric observations.

### 3. Indicator functions still assume one disease and report family per issuer

Location: outbreak_ledger/indicators.py, lines 21–29; coverage(); time_since_last_confirmed(); web.state().

The query for new confirmed counts filters issuer and geography level but not disease or report family. After select_claims correctly distinguishes disease, the function stores rows by (geography, period_end), discarding that distinction. A constructed example with approved BVD=5 and mpox=99 for the same issuer/place/date returns one result, 99, without the disease.

The current weekly module mostly uses idsr_notified rather than confirmed, so this specific overwrite is a counterexample to the shared function, not proof that the bundled weekly fixture already triggers it. There is also an immediate family-boundary problem: coverage and elapsed-time logic collect all documents from the same issuer. INSP daily and weekly reports share INSP-RDC, so weekly reports can be treated as missing daily coverage and falsely withhold BVD results.

Required change: scope indicator inputs and reporting calendars to event, disease, issuer, family, geography, classification and period definition. Use candidate period_start and period_end for weekly observations and separate publication date from reporting period. Return the event key with every output.

### 4. Issue threads can join statements from different diseases

Location: outbreak_ledger/qualitative.py, thread_statements(), especially lines 434–452.

Matching requires common family, issuer, topic, geography and overlapping words, but not disease/event. Two constructed laboratory-shortage statements for cholera and mpox were joined into one two-report issue thread. A shared operational constraint can legitimately affect several diseases, but that relationship must be explicit and reviewed; the current match silently assumes it.

Thread IDs are recomputed from the current row ordering each time. Importing earlier reports or retagging can renumber threads. Formerly assigned thread_id values are not cleared from statements that no longer qualify, risking stale links.

Required change: stable persisted thread identifiers; explicit event association; human confirmation of proposed links; an option for deliberately shared cross-event constraints; audited link/unlink and resolution decisions. Distinguish "suggested ongoing issue in the latest uploaded report" from a verified current operational status.

## Additional findings

### 5. Rejected statements remain in event-register totals

web.event_register() loops through all statements without excluding rejected rows. A constructed rejected cholera challenge still produces a cholera event with one statement and one challenge. Rejected evidence should remain in history, but should not count as current event evidence. Show candidate and human-reviewed summaries separately.

The event register groups by disease string alone. It does not distinguish two cholera outbreaks in different countries or separate episodes of the same disease. Its latest count selects one raw non-rejected claim by date, without presenting all simultaneous source/classification alternatives. The unverified badge is useful but does not solve event identity or competing-claim selection.

### 6. Three supplied early real BVD reports were not recognised

Automatic routing was tested on the project's available reports dated 31 May, 1 June and 2 June 2026 (filenames starting 14-, 15- and 17- in the project sources). All were returned as unrecognised. They contain readable body text, but their extracted text does not match the current module fingerprints. This shows that support for an INSP family does not establish support across its earlier layouts or image-based headers.

Required change: report why routing failed; permit a user to propose a family and confirm missing metadata, followed by validation; add representative early/late layouts to evaluation. Do not accept a report silently just by its filename. The existing refusal to count unrecognised documents as zeros should be retained.

### 7. Qualitative tag correction has validation and audit gaps

Store.review_statement() accepts arbitrary types for editable tags. A constructed retag with topics supplied as a plain string is saved, then thread calculation raises JSONDecodeError. The normal browser currently sends lists; this is a backend validation gap, not a claim that ordinary topic entry necessarily triggers it.

The browser allows type, state, topic and broad place corrections but does not expose disease/event correction or health-zone corrections. Consequently a critical disease misassignment cannot be fixed through the visible review form. The Review history tab renders numeric events only; the full API download contains statement events, but the download button is disabled when there are no numeric reviews. Qualitative-only work therefore lacks an accessible review-log download through that control.

Required change: validate typed lists and permitted values before writing; expose event and health-zone corrections; show both review histories and enable export for either kind of review.

### 8. Integrity protections differ between export types

Numeric export checks source hashes; reviewed-statement export does not. Both should enforce the same source-integrity policy and include rule/configuration version references. Configuration snapshots are retained but not sufficient for full historical replay.

### 9. Performance and validation claims need tighter boundaries

A higher batch limit is an interface limit, not proof of sustainable capacity on an ordinary laptop. Uploads are base64 JSON, extraction runs under one lock, and state responses return the full observation and statement collections. There is no background job queue, cancellation or backend pagination.

The 1,635 observations, 1,324 statements and approximately 23-second development run are claims in the supplied validation notes. The matching thirteen-PDF corpus was not supplied for this review, so those results and the earlier claimed Chromium run were not independently reproduced. The three attached development CSVs document outputs, not independent ground truth or extraction recall.

Unknown layouts, Word, Excel, CSV, webpages, scanned PDFs and photographs remain unsupported inputs. Describing the tool as accepting different diseases is accurate within configured families; describing it as supporting arbitrary outbreaks or public-health reports would overstate the evidence.

## Checks performed here

- Inspected both ZIP layers, launchers, Python modules, configuration, browser code, documentation, tests and the supplied development CSV structure/examples.
- Ran the included suite: **40 passed, 1 skipped**, Python 3.12 on Linux. The skipped test requires OL_REAL_REPORTS; that original development folder is unavailable.
- JavaScript syntax check passed with node --check.
- Ran targeted constructed-data probes for wrong narrative attribution, indicator disease collision, cross-disease issue linking, rejected-statement register inclusion and malformed tag handling. Probe outputs are included under review_evidence.
- Attempted automatic routing for three available early real BVD PDFs; none matched. This is a routing result, not an extraction-accuracy estimate.
- Did not perform Windows execution, independent browser testing, expert verification of the original development corpus, OCR/model evaluation or an operational field validation.

## Recommended next release

First fix disease/place attribution, numeric export meaning and numeric review visibility. Then introduce stable event IDs and propagate them through indicators, issue threads and review logs. Correct rejection handling, typed tag validation, source-integrity checks and qualitative history access. Add realistic negative and multi-event regression tests that reproduce the failures above.

After those repairs, evaluate multiple layouts and diseases using independently annotated held-out reports. Measure wrong-event attribution, value-and-definition accuracy, abstention, review time and correction workload. Only then add new input formats or AI extraction behind the same review interface.

For fellowship evidence, show one difficult report being correctly attributed, a conflicting claim retained, an ambiguous field withheld, a human correction logged and a second disease kept separate throughout export. That is a stronger demonstration than quoting the number of automatically detected events or extracted statements.
